# 2026-11-12 — 스탠딩 캘린더 고정 시 사라지는 버그 (Win11 24H2)

## 배경

사용자 제보:
> "스탠딩 캘린더로 고정하면 캘린더가 사라져버리는 버그가 발견됐어. 해당 pc는 win11
> 24h2 (10.0.26100) 이야. 이때 다시 캘린더 분리 버튼을 눌러도 캘린더가 나타나지
> 않아서 프로그램을 완전히 종료후에 다시 켜야 캘린더 분리창이 실행됐어."

## 조사

바탕화면 고정은 Explorer의 `Progman`/`WorkerW` 창에 캘린더 창을 `SetParent`로
재부모시키는 방식(`src/win_style.rs`의 `desk::pin`)으로 동작한다. Windows 11
24H2는 이 셸 구조를 바꿔서 여러 바탕화면 꾸미기 프로그램(Wallpaper Engine 등)이
한동안 고장났던 적이 있는, 잘 알려진 OS 레벨 변경이다. 기존 코드에는 이미 이
변경에 대응하는 처리("Windows 11 24H2: the WorkerW is a child of Progman")가
있었다.

실제 사용자의 24H2(10.0.26100) 기기에 직접 접근할 수는 없었지만, 연결된
PC(Windows 11 25H2, 빌드 26200 — 24H2 이후 빌드로 같은 계열의 셸 구조를 가짐)에서
실제 앱을 통해 라이브로 재현·검증했다:

1. 실제 셸 계층을 진단하는 코드를 앱에 임시로 추가해 확인한 결과, 이 PC에서는
   `SHELLDLL_DefView`가 `Progman`의 직계 자식이고, 바탕화면 레이어로 쓸 진짜
   `WorkerW`도 `Progman`의 자식(최상위 창이 아님)으로 존재했다. 즉 기존 24H2
   대응 fallback 코드가 정확히 이 창을 찾아낸다 — **레이어를 못 찾는 문제는
   아니었다.**
2. 실제 UI로 스탠딩 버튼을 눌러본 결과, 고정과 해제 모두 이 PC에서는 정상
   동작했다(아이콘 밑에 정확히 깔렸고, 다시 누르니 정상적으로 복귀).
3. 코드를 다시 읽는 중 `src/win_style.rs`의 `pin()`에서 `SetParent`의 반환값을
   전혀 확인하지 않고 항상 `true`(성공)를 반환하는 결함을 발견했다. `SetParent`는
   실패 시 null을 반환하는데, 이 경우를 무시하면: 재부모가 실제로는 안 됐는데도
   `standing`이 `Some(...)`으로 설정되고 제목표시줄은 이미 제거된 채로 남고,
   "바탕화면 클릭 감지" 후킹은 엉뚱한 자리를 감시하게 된다. 이후 매 프레임
   동일한(이미 고정된 것으로 간주되는) 뷰포트가 계속 그려지므로, "캘린더 분리"
   버튼을 다시 눌러도 `state`가 이미 `Window`라서 아무 효과가 없다 — 사용자가
   보고한 "다시 눌러도 안 나타나고 재시작해야만 해결됨"과 정확히 일치하는
   증상이다.

이 PC에서는 `SetParent` 자체가 항상 성공했기 때문에 이 결함이 직접 재현되지는
않았지만, 어떤 이유로든(권한/타이밍/다른 24H2 빌드별 차이 등) `SetParent`가
실패하는 환경이라면 100% 이 "고착" 버그로 이어지는 구조적 문제였다.

## 변경 내용

`src/win_style.rs`의 `desk::pin()`에서 `SetParent`의 반환값을 확인하도록
수정 — null(실패)이면 그 자리에서 `false`를 반환하고 재부모 작업을 더 진행하지
않는다. 호출 쪽(`calendar_dock.rs`의 `standing_frame`)은 이미 `pin_to_desktop`이
`false`를 반환하면 `self.cal.standing`을 `None`으로 되돌리는 처리가 있었으므로,
다음 프레임부터 제목표시줄이 복구된 정상 창으로 돌아간다. 즉 재부모가 실패해도
창이 "사라진 채 고착"되지 않고 그냥 평소대로 쓸 수 있는 창으로 남는다.

## 검증

- Linux: `cargo build` / `cargo clippy --all-targets` / `cargo fmt -- --check`
  모두 깨끗하게 통과.
- Linux: `cargo test` — 113 passed, 1 failed (기존부터 있던, Windows 전용 폰트가
  없어서 Linux 컨테이너에서만 실패하는 테스트, 이번 변경과 무관).
- Windows (실제 PC, 11 25H2/26200): `cargo build` 성공, `cargo test` —
  **114 passed, 0 failed**.
- 실제 UI로 스탠딩 고정 → 해제 전체 흐름을 라이브로 재현·확인함(스크린샷으로
  바탕화면 아이콘 밑에 정확히 깔리는 것, 클릭 시 정상 복귀하는 것 확인).
- `SetParent` 실패 자체를 인위적으로 재현하지는 못했다(이 PC에서는 항상
  성공) — 수정은 `SetParent`의 공식 실패 반환 규약에 기반한 것이며, 실제
  실패 상황을 라이브로 재현해 검증한 것은 아니다.

## 남은 것 / 확인 요청

이번 수정으로 "고정 실패 시 고착되는" 결함은 구조적으로 막았지만, 사용자가 보고한
정확한 24H2(10.0.26100) 빌드에서 애초에 **왜** `SetParent`가 실패했는지(또는
정말 실패한 게 맞는지)는 그 기기에서 직접 확인하지 못했다. 다음에 그 PC에서
다시 테스트해보고, 혹시 또 사라지는 증상이 재현되면:
- 재현 직후 바로 (재시작 없이) "캘린더 분리" 버튼을 다시 눌러서 정상 창으로
  복귀되는지 확인 부탁드립니다. 이번 수정이 제대로 작동한다면 복귀되어야 합니다.
- 그래도 안 되면 그 PC의 정확한 Windows 빌드 번호(`winver`)와, 가능하면 바탕화면
  아이콘 표시 여부(설정에서 켜져 있는지)를 알려주시면 추가로 조사하겠습니다.
  (일부 24H2 초기 빌드는 바탕화면 아이콘이 꺼져 있을 때 비슷한 부류의 버그가
  보고된 적이 있습니다.)
