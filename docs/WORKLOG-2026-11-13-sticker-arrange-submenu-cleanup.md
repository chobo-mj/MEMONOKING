# 2026-11-13 스티커 더보기>정렬 메뉴 구조 재정비 (#58)

## 요청
"스티커 더보기>정렬 메뉴 구조 재정비" — 스티커의 "더보기 › 스티커 정렬" 서브메뉴 구조를
정리해달라는 요청.

## 조사
- `src/studio.rs`의 `sticker_menu(ui, i, w, own)`가 우클릭 메뉴(Context, `own = true`)와
  더보기의 스티커 정렬 서브메뉴(`SubMenu::Arrange`, `own = false`) 양쪽에 재사용되고 있었다.
- `own`은 맨 위의 "잠금 해제…"/"스티커로 펼치기" 행만 가렸고, 맨 아래의 "이 스티커 닫기"/
  "모든 스티커 닫기 Ctrl+Shift+H"는 `own` 값과 무관하게 항상 표시됐다. 그 결과 "더보기 › 스티커
  정렬" 서브메뉴를 열면 정렬 옵션 6개 아래에 **정렬과 무관한 닫기 명령 2개**가 또 붙어 있었다 —
  우클릭 메뉴에 이미 있는 항목이 엉뚱한 곳에 중복되는 구조였다.

## 구현
- `src/studio.rs`: 닫기 2개 버튼(과 그 앞 구분선)을 `if own { ... }`로 감싸, 서브메뉴
  (`own = false`)에서는 정렬 옵션만 남고 우클릭 메뉴(`own = true`)에서는 기존처럼 닫기 명령이
  그대로 보이게 했다.
- 새 테스트 `arrange_submenu_omits_the_close_actions_the_context_menu_still_has` — 실제 egui
  프레임을 렌더링해 우클릭 메뉴에는 "이 스티커 닫기"가 보이고, 더보기의 정렬 서브메뉴에는 보이지
  않으면서 정렬 옵션은 그대로 남아 있는지 확인.

## 가정 (명시)
- "구조 재정비"를 "정렬과 무관한 항목 제거"로 해석했다. 정렬 옵션 자체의 순서나 문구 변경, 추가
  정렬 옵션 신설은 요청에 없다고 보고 진행하지 않았다. 다른 재구성을 의도한 것이라면 알려주시면
  추가로 조정하겠다.

## 시험
- Linux: `cargo test` 128개 중 127 통과(윈도우 전용 글꼴 경로 테스트 1개는 기존 실패, 회귀 아님),
  `cargo clippy --all-targets` 경고 없음, `cargo fmt --check` 통과.

## 후속 수정 — 정렬 메뉴 2단 구조로 재편 (비주얼 검증에서 추가 요청)

위의 "닫기 중복 제거"로는 부족했다. 실제 화면에서 보니 "스티커 정렬" 서브메뉴가 여전히
정렬 방향 3개(오른쪽/왼쪽/계단식) + 방향과 모드를 억지로 묶은 조합 항목 3개("모두 제목만
보이게 · 오른쪽 정렬" 등)가 평평하게 나열되어 있어 혼란스럽다는 피드백을 받았다. 요청한
새 구조:

- "화면 오른쪽에 정렬" → 그 안에 "모두 제목만 보이게" / "모두 상자로접기" / "모두펼치기"
  3개를 담은 **새 팝업**을 연다 (오른쪽 정렬 + 선택한 모드로 한번에 적용).
- "화면 왼쪽에 정렬" → 동일한 3개 옵션의 새 팝업을 연다 (왼쪽 정렬 버전).
- 기존 "1차 팝업"에 있던 조합 항목 3개("모두 제목만 보이게 · 오른쪽 정렬", "모두 상자로
  접기 · 오른쪽 정렬", "모두 펼치기 · 계단식 정렬")는 삭제.
- "계단식으로 정렬"은 방향/모드를 섞지 않는 단독 동작이라 그대로 유지(새 구조에 언급되지
  않았고 삭제 대상 목록의 문구("…계단형으로 모두펼치기")도 사실은 옛 조합 항목 중
  "모두 펼치기 · 계단식 정렬" 하나를 가리키는 것으로 해석함).

### 구현
- `src/studio.rs`:
  - `Menu` 구조체에 3번째 팝업 레벨을 위한 `sub2: Option<(Layout, f32)>` /
    `sub2_size: Vec2` 필드 추가. 기존 `sub`/`sub_size`가 "더보기 → 스티커 정렬" 1단계
    팝업을 담당하던 패턴을 그대로 한 단계 더 반복한 것.
  - `sticker_menu(ui, i, w, own, sub2)`: "화면 오른쪽/왼쪽에 정렬"을 즉시 정렬하는
    버튼에서 `submenu_row`(기존 "프로젝트 설정"/"스티커 정렬" 행과 동일한 호버-오픈 패턴)로
    변경. 옛 조합 항목 3개와 그 앞 구분선은 제거. "계단식으로 정렬"은 그대로 즉시-동작
    버튼으로 남김.
  - 새 함수 `arrange_side_menu(ui, layout)`: 해당 방향(layout)에 대해 "모두 제목만
    보이게"/"모두 상자로 접기"/"모두펼치기" 3개 버튼을 그리고, 클릭 시 `self.arrange`를
    설정.
  - `sticker_menu_window`: `sub2`를 `sub`와 같은 방식으로 프레임 간 유지하고, 활성화되면
    세 번째 `menu_window`를 띄운다. 위치는 기존 `submenu_pos` 규칙을 그대로 재사용하되,
    기준 사각형(parent rect)은 상황에 따라 다르게 잡는다 — 우클릭 메뉴(Context)에서 열렸으면
    메뉴 자체의 창을, 더보기 › 스티커 정렬에서 열렸으면 그 서브메뉴 창을 기준으로 옆에 띄운다.

### 가정 (명시)
- "팝업을 신규 추가하는거야. 팝업창 디자인과 생성위치 규칙은 기존 룰을 참고해"를 이
  코드베이스에 이미 있는 `menu_window` + `submenu_pos`(더보기 → 스티커 정렬이 이미
  이렇게 옆에 떠 있음) 패턴을 그대로 재사용하라는 뜻으로 해석했다. 새로운 시각 디자인이나
  위치 계산 로직을 따로 만들지 않았다.
- 이 2단 구조는 우클릭 메뉴(Context, `own = true`)와 더보기 › 스티커 정렬
  (`SubMenu::Arrange`, `own = false`) **양쪽 모두**에 동일하게 적용했다. 두 메뉴가
  `sticker_menu` 함수를 그대로 공유하고 있고, 요청에서 두 경로를 다르게 만들라는 언급이
  없었기 때문에 한쪽만 바꾸면 오히려 더 혼란스러울 것으로 판단했다.
- "계단식으로 정렬"의 운명이 요청 문구에서 가장 모호했다(새 구조 설명에는 등장하지 않지만
  삭제 대상으로도 명시되지 않음). 삭제 대상 문구 "계단형으로 모두펼치기"를 옛 조합 항목
  "모두 펼치기 · 계단식 정렬" 하나로 읽어, 단독 "계단식으로 정렬" 버튼은 유지했다. 이 해석이
  틀렸다면 바로 알려주시면 삭제하겠다.

### 시험
- 새 테스트 4개 (`studio::arrangement_tests`):
  - `arrange_menu_no_longer_offers_the_old_combined_position_and_mode_items` — 옛 조합
    항목 3개가 우클릭/더보기 양쪽에서 모두 사라졌고 "계단식으로 정렬"은 남아있는지 확인.
  - `clicking_the_right_side_row_opens_its_popup_instead_of_arranging_immediately` —
    "화면 오른쪽에 정렬" 행을 호버하면 즉시 정렬되지 않고 `sub2`만 열리는지 확인.
  - `arrange_side_menu_arranges_with_the_clicked_fold_mode` — 새 팝업에서 "모두 상자로
    접기"를 클릭하면 지정한 방향(Layout::Left)과 모드(Mode::Swatch)로 정확히 정렬되는지
    확인.
  - 기존 `arrange_submenu_omits_the_close_actions_the_context_menu_still_has`는 새
    `sub2` 파라미터만 추가해 계속 통과.
