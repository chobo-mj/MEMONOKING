# 별도 창·캘린더·알림 개발 계획

> 상태: 설계 기준안. 기존 Windows 프로그램의 UI·프로세스·저장 구조와 사내 실행 정책을 분석한 뒤 적용한다. 운영체제에서 보장하지 않는 전면 표시나 꺼진 PC의 알림을 제품 보장으로 약속하지 않는다.

v1.1 확장: 정기 일정은 핵심 범위다. [02 공통 모델](02-data-states.md), [09 반복·예외·범위별 이동](09-recurring-schedules.md), [10 색상 라벨](10-bookmarks-labels.md)과 함께 구현한다.

v1.3 확장: [13](13-capture-views-checklists.md)의 전역 빠른 입력·수집함·저장 보기·체크와 [14](14-status-overlap-journal.md)의 진행 상태·겹침 안내·일지 진입점을 기존 화면에 연결한다. 메모별 변경 이력 화면은 추가하지 않는다.

## 1. 선행 조사와 기본 정책

다음 항목을 실제 폐쇄망 PC와 동일한 정책의 시험 환경에서 확인한다.

- 프로그램 종료·트레이 숨김·최소화의 현재 차이, 자동 시작 허용 여부.
- 지원 Windows 버전·아키텍처·배율, 다중 모니터, 원격 접속, 절전·최대 절전 사용 방식.
- 별도 창·트레이·작업표시줄·Windows 알림 사용 가능 여부와 보안 에이전트 간섭.
- 사내 잠금 화면에서 민감한 제목·본문을 노출해도 되는지.
- 바탕화면에 창을 두는 방식이 운영체제·보안 정책과 호환되는지.
- 기존 날짜가 종일 날짜인지, 로컬 시각인지, UTC인지. 날짜만 있는 과거 데이터의 해석 근거.
- 승인된 한국 공휴일 패키지를 반입·검증하는 절차. 공휴일의 생성·갱신은 별도 공휴일 모듈 담당이다.

기본 범위는 로컬 사용자 세션에서 실행되는 프로그램이다. Windows 서비스, 관리자 권한 상주 프로그램, 예약 작업·절전 깨우기는 사전 채택하지 않는다. 프로그램이 완전히 종료되어 있거나 PC가 꺼져 있으면 즉시 알림을 낼 수 없으며, 다음 실행 때 놓친 알림을 처리한다.

## 2. 요구사항

| ID | 기능 | 수용 조건 |
|---|---|---|
| WIN-01 | 스티키 창 분리 | 메모를 독립 창으로 열고 크기·위치를 조절한다. 같은 메모를 다시 열면 기존 창을 찾아 활성화하는 것을 기본으로 한다. |
| WIN-02 | 창 상태 보존 | 재실행 시 허용된 창을 유효한 모니터 안에 복원한다. 화면 밖 좌표를 그대로 적용하지 않는다. |
| WIN-03 | 접기·항상 위 | 제목줄만 보이는 접힘과 전체 보기를 지원한다. 항상 위는 사용자 선택이며 알림 때문에 영구 변경하지 않는다. |
| WIN-04 | 분리 캘린더 | 메인 창과 같은 일정 저장소를 보는 독립 캘린더 창을 제공한다. |
| WIN-05 | 선택적 바탕화면 표시 | 후속 선택 기능. 안정적 방식·보안 승인·기능 저하 대응이 검증된 경우에만 제공한다. |
| WIN-06 | 좌우 분할 | 왼쪽 메모 목록/트리, 오른쪽 캘린더를 표시한다. 분할비를 저장하고 키보드로 조절한다. |
| CAL-01 | 일정 생성·이동 | 메모를 날짜·시간 칸에 드롭해 일정 생성. 이미 캘린더 안에 있는 항목도 다른 날짜로 끌어 이동하며 원본 메모를 복제하지 않는다. 반복은 REC 범위 선택을 따른다. |
| CAL-02 | 원본 연결 | 일정 선택 시 원본 메모를 열고 원본 변경을 즉시 반영한다. |
| CAL-03 | 완료 표시 | 단발/전체 메모 완료와 반복 한 회차 완료를 구분한다. 해당 범위에 취소선·체크 표식을 표시하고 다른 회차를 암묵 완료하지 않는다. |
| CAL-04 | 종일·시간 일정 | 날짜만 있는 종일 일정과 시각이 있는 일정을 분리한다. |
| CAL-05 | 공휴일 | 오프라인 데이터의 명칭·종류·버전·검증 범위를 표시한다. 알 수 없는 연도는 정확한 공휴일이라고 표시하지 않는다. |
| CAL-06 | 접근 가능한 일정 편집 | 드래그 없이 날짜·시각 입력과 키보드 이동이 가능하다. |
| REM-01 | 메모·회차별 알림 | 단발 절대/상대 알림, 반복 회차별 상대 알림을 설정한다. 종일 반복의 매회 알림은 명시 기준 시각·시간대를 필수로 받고 자동 자정을 사용하지 않는다. |
| REM-02 | 창 펼치기·주의 환기 | 알림 때 접힌 창을 펼치고 복원·전면 표시를 시도한다. 허용되지 않으면 작업표시줄 강조·앱 내 미확인함으로 알린다. |
| REM-03 | 놓친 알림 | 절전 복귀·재실행·시계 변경 후 놓친 알림을 찾아 요약하고 확인·다시 알림을 제공한다. |
| REM-04 | 중복 억제 | 같은 알림 발생 건의 논리 ID를 유지해 창과 목록의 중복 생성을 막는다. 장애 경계에서는 재표시될 수 있음을 고려한다. |
| REM-05 | 확인·다시 알림·취소 | 사용자 응답과 재시도 상태를 영속 저장한다. 완료·휴지통 이동·일정 변경과 일관성을 유지한다. |

월 보기를 기본으로 구현하고, 주·일 보기는 시간 일정의 필요성과 기존 화면 재사용 가능성을 보고 단계적으로 추가한다. 매일·매주·선택 요일·평일·주말 반복과 이번만/이후 이동은 이번 범위다. 한 메모의 복수 독립 일정 정의와 업무 자원 예약은 별도 범위다.

## 3. 일정 데이터와 시간 의미

### 3.1 단일 원본 일정

메모당 최대 한 개의 기본 `Schedule` 정의를 둔다. 단발은 이 레코드의 날짜를, 반복은 연결된 RecurrenceSeries·예외·회차 상태를 조회한다. 여러 회차를 여러 메모로 복제하지 않는다.

```text
Schedule(
  id PK, note_id UNIQUE,
  mode: once | recurring,
  kind: none | all_day | timed (once 전용, recurring은 null),
  start_date, end_date_exclusive,
  start_at_utc, end_at_utc,
  time_zone,
  schedule_revision
)
```

| kind | 저장 의미 | 검증 |
|---|---|---|
| `none` | 일정 없음. 삭제된 일정과 알림 이력을 구별할 필요가 있으면 레코드를 유지할 수 있다. | 날짜·시각 값은 null |
| `all_day` | 시작 날짜 이상, 종료 날짜 미만의 민간력 날짜 구간. 하루 일정은 종료가 다음 날 | `start_date < end_date_exclusive`, UTC 시각은 null |
| `timed` | 실제 시점 구간을 UTC로 저장하고 입력·표시에 쓴 시간대를 보존 | `start_at_utc < end_at_utc`, 종일 날짜 필드는 null |

위 kind·날짜·시각 필드는 단발 전용이다. recurring에서는 null로 두며 각 세그먼트의 kind(all_day/timed)·로컬 anchor·요일 집합·기간·시간대가 원본이다. 상세 스키마는 02·09를 사용하고 화면에서 별도 반복 날짜 목록을 원본처럼 저장하지 않는다.

시간대 기본값은 초기 설정에서 확인하며 대한민국 업무 환경이면 `Asia/Seoul` 같은 의미상의 표준 시간대를 사용한다. Windows ID와 IANA ID 중 실제 저장 방식은 스택에 따라 정하되 변환 표의 버전을 관리한다. 운영체제의 현재 시간대를 바꾸었다는 이유로 기존 종일 날짜를 UTC로 이동시키지 않는다.

단일 시점 마감만 필요한 경우에도 임의의 1시간 길이를 몰래 만들지 않는다. 기존 요구가 마감일 중심인지 일정 구간 중심인지 코드 분석·사용자 확인 항목으로 남기고, 기준안은 날짜 또는 명시적 시작·종료 구간이다. UI에서 시간 일정을 새로 만들 때 제안하는 길이는 설정으로 보여 주고 확정하게 한다.

일정 수정 명령은 `expected_revision`으로 Note 원본 버전과 `expected_schedule_revision`으로 일정 버전을 모두 검증한다. 반복은 관련 series/exception/state revision도 검사한다. 성공하면 해당 원본 revision을 함께 증가시킨다. 회차 상태만 변경한 경우 Note 전체 완료를 변경하지 않는다. 일정과 그 변경으로 취소·재계산되는 상대 알림은 같은 저장 단위 또는 복구 가능한 작업 기록으로 일관되게 처리한다.

### 3.2 달력 표시와 완료

- 날짜 셀의 `메모 추가` 또는 키보드 Enter로 제목·짧은 본문을 입력하는 빠른 입력을 제공한다. 확인할 때 새 Note와 해당 날짜의 하루 종일 Schedule을 하나의 명령으로 확정하고 취소하면 둘 다 만들지 않는다. 일정 없는 메모를 먼저 만든 후 연결을 잊는 중간 상태를 숨겨 생성하지 않는다. 세부 시각·기간은 확장 입력에서 명시한다.
- 월 경계에 걸친 종일 구간은 종료일 미만 규칙을 적용한다. 11월 8~9일 이틀은 저장 구간 `[11-08, 11-10)`이다.
- 단발/전체 메모 완료는 `Note.completed_at_utc`에서, 반복 한 회차 완료는 `OccurrenceState`에서 조회한다. 달력의 회차 체크는 그 회차만 완료한다. ‘메모 전체 완료·반복 중지’는 범위를 안내하는 별도 동작이다.
- 완료해도 일정은 달력에 남고 취소선·체크 표식으로 보인다. `완료 숨기기` 필터는 선택 사항이다.
- 종일·시간 일정이 같은 날이면 종일 영역과 시간 영역을 구별한다. 월 보기 안의 표시 개수 제한에는 `외 N개` 펼치기를 제공한다.
- 한 메모의 반복 건이 여럿 보여도 기본 일정 정의는 하나다. 캘린더 삭제는 `이번 일정 취소`, `이 날짜 이후 반복 종료`, `전체 일정 해제`, `메모 휴지통 이동`을 구분하고 과거 완료 이력을 보존한다.
- 한국 공휴일은 일정과 다른 레이어로 보여 사용자의 메모가 공휴일 데이터 갱신 때문에 변경되지 않게 한다.
- 반복 항목에는 반복 표식과 원래 회차·임시 이동 상태를 표시한다. 라벨은 Note의 상단 색띠·이름 배지로 공유하고, 달력 항목에도 라벨 표식과 같은 any/all 필터를 적용한다. 같은 날짜에 겹친 서로 다른 회차를 병합하지 않는다.

## 4. 창과 좌우 분할

### 4.1 창 레지스트리

논리 창 정보 `WindowState(window_id, kind, note_id?, selected_occurrence_key?, normal_bounds_dip, monitor_hint, display_scale_hint, collapsed, always_on_top, is_visible, last_opened_at)`를 별도 화면 설정으로 관리한다. 이 설정 변경은 메모 본문 revision을 바꾸지 않는다.

- 메모 스티키는 기본적으로 메모당 하나를 재사용한다. 같은 메모의 다중 편집 창이 기존 프로그램에 꼭 필요하다면 모든 창에 같은 revision 계약을 적용한다.
- 반복 회차에서 스티키를 열면 정규 회차 키와 실제 날짜를 헤더에 표시한다. 같은 Note의 다른 회차로 창을 재사용하면 컨텍스트를 명시 갱신하고 체크 대상 날짜를 보여준다. 알림 카드의 확인·완료는 카드에 보관한 키를 사용하며, 현재 스티키가 다른 회차로 바뀌었다고 체크 대상을 바꾸지 않는다. 같은 Note의 서로 다른 회차 알림을 하나의 확인 상태로 합치지 않는다.
- 메인 창을 닫는 동작, 메모 창만 닫는 동작, 트레이로 숨기는 동작, 앱을 종료하는 동작을 구분한다.
- 메모 창 닫기는 메모 삭제·일정 해제·알림 취소를 뜻하지 않는다.
- 알림은 창이 닫혀 있어도 메모를 다시 열 수 있다. 휴지통 메모나 영구 삭제 메모는 열지 않는다.
- 창 크기는 화면 독립 단위로 보관하고 복원 시 현재 배율로 계산한다. 최소 크기와 화면 경계 안으로 보정한다.
- 모니터가 사라졌으면 주 모니터의 안전한 위치로 복원한다. 작업표시줄·가용 작업 영역을 침범하지 않게 한다.
- 최대화·최소화 상태와 일반 창 좌표를 구별한다. 마지막 최소화 상태 때문에 새 실행 시 모든 창이 보이지 않는 상황을 피한다.
- 창 이동·크기 변경은 적절히 지연 저장한다. 마우스 이동마다 DB에 쓰지 않는다.

### 4.2 좌우 분할

왼쪽은 트리/목록과 선택 메모로 이동하는 기능, 오른쪽은 캘린더를 둔다. 기존 편집기 배치와 충돌하면 중앙 편집 영역 또는 별도 편집 창으로 조정하되 사용자가 메모와 달력을 동시에 비교할 수 있어야 한다.

분할비, 선택 날짜, 선택 메모, 필터는 화면 설정으로 둔다. 창이 좁으면 최소 폭을 보장하고 탭 전환을 제공한다. 좁은 화면에서도 드래그 없이는 일정을 넣을 수 없는 구조를 만들지 않는다. 드래그 중 자동 스크롤 속도는 제한하고 드롭할 날짜를 명확히 강조한다.

### 4.2.1 빠른 입력과 저장 보기 연결

전역 단축키는 실행 중인 앱에 등록하고 빠른 입력창은 초안 1개를 재사용한다. 창 열기만으로 Note를 만들지 않고 명시 저장 시 수집함 Note 1개를 확정한다. 키 등록 거부·IME·다중 모니터·앱 완전 종료를 구별하며 본창/트레이 버튼을 대체 진입점으로 둔다. 전역 키 수집·클립보드 자동 감시는 없다.

이름 있는 보기는 메모/달력의 필터·정렬 정의이며 현재 화면의 임시 변경과 분리한다. 공유 split·분리 캘린더에 같은 기준일·시간대·조건 revision을 적용하고 독립 보기 여부를 표시한다. 이미 열린 스티키를 필터 때문에 강제 닫지 않는다. 상태·체크 표시도 원본 Note/선택 회차 범위를 헤더에 명확히 표시한다.

### 4.3 바탕화면 표시 선택안

바탕화면에 ‘박힌’ 캘린더는 두 방식이 서로 다르다.

| 방식 | 가능한 동작 | 제한·검토 |
|---|---|---|
| 바탕화면용 고정 창 | 상호작용 가능한 달력, 크기 조절 가능 | 다른 창과의 쌓임, 바탕화면 보기, 탐색기 재시작 시 동작 검증 필요 |
| 실제 배경 그림 생성 | 안정적인 정적 시각화 | 클릭·드래그·실시간 갱신 어려움. 배경에 민감 일정이 남을 수 있음 |

기본 배포는 별도 캘린더 창이다. 선택 기능은 문서화된 API·공식 지원 가능성을 먼저 확인한다. Windows 내부 창 계층에 의존하는 비공식 부착을 필수 기능으로 삼지 않는다. 기능 장애가 발생해도 일반 캘린더로 즉시 돌아올 수 있어야 하며 화면 잠금·화면 공유 노출 정책을 검토한다.

## 5. 드래그 일정 명령

단발 명령 예시는 `SetSchedule(note_id, expected_revision, expected_schedule_revision, proposed_schedule, command_id)`다. 반복에는 `PreviewOccurrenceMove` 후 `MoveOccurrenceOnly` 또는 `MoveThisAndFuture`를 사용한다. 반복 슬롯의 정규 키·현재 주소·규칙/예외 revision과 미리보기 토큰을 포함한다. Note와 Schedule 중 어느 예상 버전이 달라도 충돌을 확인한다. UI에서 미리 이동한 모양을 보여 줄 수 있지만 저장 실패 시 이전 위치로 돌리고 실패 상태를 유지한다.

| 시작 위치 → 목적지 | 의미 |
|---|---|
| 일정 없는 메모 → 월 보기 날짜 | 종일 하루 일정 생성 |
| 기존 종일 일정 → 다른 날짜 | 시작일 이동, 기존 날짜 길이 유지 |
| 기존 시간 일정 → 월 보기 날짜 | 현지 시작 시각과 실제 구간 길이를 유지해 날짜 이동. 종일 변환은 별도 명령 |
| 캘린더의 반복 회차 → 다른 날짜 | 목표일 강조 후 ‘이번 일정만 / 이 날짜 이후 모두’ 선택. 예외 변경 또는 세그먼트 분할로 반영 |
| 메모 → 주/일 시간 칸 | 해당 시각 제안. 시간대·종료 시각 확인 가능 |
| 일정 막대 끝 조절 | 구간 길이 변경. 별도 크기 변경 피드백과 최소 길이 검증 |
| 캘린더 항목 → 관련 메모 영역 | 일정 변경 없이 원본 메모 관계 연결 |
| 창 밖·금지 영역·Escape | 저장 변경 없음 |

여름시간이 있는 시간대를 지원한다면 존재하지 않는 현지 시각·두 번 존재하는 시각을 조용히 보정하지 않는다. 선택 또는 보정 내용을 표시한다. 한국 시간만 지원하는 첫 버전이라면 시간대 변경 기능을 제한하고 그 범위를 문서에 남긴다.

드래그 시작 후 다른 창에서 메모 또는 일정이 수정되면 드롭 시 Note revision과 schedule_revision 충돌을 확인한다. 원래 일정과 현재 일정, 제안 일정을 보여 주고 최신 메모 상태에서 다시 적용하도록 한다. 달력 UI가 갖고 있는 오래된 날짜나 완료 상태로 최신 원본을 덮어쓰지 않는다.

### 5.1 반복 일정 드래그의 필수 UX

1. 반복 회차를 잡으면 목표 날짜와 기존 날짜·기간을 보여준다. 월 경계는 제한된 자동 스크롤/월 전환으로 넘어갈 수 있으며 키보드 날짜 변경도 같은 명령을 쓴다.
2. 드롭 후 ‘이번 일정만’과 ‘이 날짜 이후 모두’를 고르게 한다. 초기 기본 선택만으로 자동 저장하지 않고 취소를 제공한다.
3. 이번만은 선택 건만 목표일로 이동하고 다음 반복은 유지한다. 이후는 원래 회차 순서에서 선택 건 포함 이후를 새 규칙 구간으로 바꾼다.
4. 이후 이동의 새 요일·종료·다음 여러 회차·기존 예외·완료/확인 기록 처리 결과를 미리 보여준다. 예: 매주 월요일 한 건을 수요일로 이후 이동하면 해당 회차부터 수요일, 이전 월요일 이력은 유지한다.
5. 이미 임시 이동한 회차의 이후 이동도 원래 키로 경계를 잡는다. 선택 건은 드롭 목표일에 맞추고 나머지 기존 예외는 실제 날짜 보존을 기본으로 한다. 상세 delta·별칭·후속 구간 처리는 09를 따른다.
6. 완료된 회차는 먼저 완료 취소하도록 안내한다. 지난 미완료 건도 이번만/이후 범위를 선택해 옮길 수 있으나 선택 외의 과거·완료 기록은 보존한다. 과거 날짜로 옮길 때 알림을 즉시 쏟아내지 않는다.
7. 선택·미리보기 중에는 저장하지 않으며 확정 시 전체 변경을 원자적으로 적용한다. 실패·취소는 원래 위치, 성공 후 모든 창은 같은 결과를 표시하고 revision이 허용하면 전체 작업을 되돌린다.

### 5.2 시간 일정 겹침 안내

단발/반복 이동 미리보기에서 유효한 시간 구간의 교차를 검사한다. `A.start < B.end && A.end > B.start`만 겹침이며 종료와 시작이 맞닿으면 제외한다. 자기 정규 회차만 제외하고 같은 메모의 다른 회차·이동 예외·필터로 숨긴 일정도 포함한다. 완료/휴지통/취소는 기본 제외, 종일은 시간 점유가 아니다.

겹침은 안내이며 ‘그대로 저장’과 ‘다시 조정’을 제공한다. 무한 반복 이후 이동은 검증한 범위·미검사·실패를 명시하고 모든 미래가 안전하다고 표시하지 않는다. 미리보기 뒤 다른 일정이 바뀌면 저장 전후 재계산하되 원본을 자동 이동·삭제하지 않는다. 숨긴 충돌을 열어도 저장 보기 정의를 덮지 않는다. 상세 OVERLAP-01~06은 14를 따른다.

## 6. 알림 모델과 상태기계

### 6.1 설정과 발생 건 분리

```text
Reminder(
  id, note_id, schedule_id?, scope: note_once | series_relative,
  trigger_kind: absolute | relative,
  absolute_at_utc, offset_seconds, all_day_anchor_local_time?, anchor_time_zone?,
  generation, enabled
)

ReminderOccurrence(
  id, reminder_id, generation, schedule_occurrence_key?, delivery_revision, scheduled_at_utc,
  status: scheduled | claimed | awaiting_ack | snoozed | acknowledged | cancelled,
  claim_until_utc, next_attempt_at_utc
)
```

`Reminder`는 사용자 설정이고 `ReminderOccurrence`는 실제로 알려야 할 한 번의 사건이다. 메모당 활성 설정 하나를 기준으로 하되 반복 설정에서는 각 회차의 발생 건을 구별한다. 알림 자체를 일정과 무관한 주기로 반복하는 기능은 별도지만 정기 일정의 매회 알림은 이번 범위다.

- 절대 알림은 명시한 실제 시각을 따른다. 일정 날짜를 옮겨도 자동 이동하지 않고 화면에서 이를 설명한다.
- 상대 알림은 일정 시작 기준 `offset_seconds`를 더한다. 예: 10분 전은 -600.
- 종일 단발은 명시 절대시각을 사용한다. 종일 정기 일정의 ‘매회 알림’은 사용자가 all_day_anchor_local_time과 anchor_time_zone을 명시해야 활성화하며 기준시각 없는 자동 00:00 알림을 만들지 않는다.
- 알림 설정 자체의 변경·해제·전체 완료·삭제는 `generation`을 증가시킨다. 이번 회차 이동은 해당 건의 `delivery_revision`으로 과거 전달을 무효화하며 다른 회차 확인·미루기 상태는 유지한다. 이후 분할은 정규 슬롯 identity·상태를 유지하고 해당 규칙/예외 revision을 재검사한다.
- `(reminder_id, generation, schedule_occurrence_key)`에 논리 고유성을 둔다. 반복 키는 `(lineage_id,global_ordinal)`, 단발 키 없음은 sentinel이다. 다시 알림은 같은 건의 next_attempt_at_utc를 갱신하며 원래 scheduled_at_utc와 알림 ID를 유지한다. 슬롯 주소가 분할로 바뀌어도 같은 정규 회차의 확인을 되살리지 않는다.
- 상세 시도 횟수·마지막 오류·처리 이력은 별도 전달 시도 기록에 둘 수 있다. 메모 본문이나 이미지가 진단 로그에 섞이지 않게 한다.

### 6.2 상태 전이

```text
scheduled --기한 도래·원자적 선점--> claimed
claimed --영속 앱 알림함 기록--> awaiting_ack
claimed --알림함 기록 전 장애·lease 만료--> scheduled (재시도)
awaiting_ack --사용자 확인--> acknowledged
awaiting_ack --다시 알림 선택--> snoozed
awaiting_ack --재시작 후 재전달 필요·선점--> claimed
snoozed --next_attempt 도래·선점--> claimed
scheduled/claimed/awaiting_ack/snoozed --설정 변경·완료·삭제--> cancelled
```

`claimed`의 `claim_until_utc`는 실행 담당자가 멈추었을 때 다른 실행 또는 다음 실행이 인계할 수 있게 하는 유효기간이다. 한 사용자 앱 단일 프로세스여도 이 상태를 영속화해 비정상 종료에서 복구한다. 여러 앱 인스턴스가 같은 데이터 경로에 접근하지 못하게 하는 잠금도 별도로 둔다.

`awaiting_ack`는 영속 앱 알림함에서 사용자 확인을 기다린다는 뜻이다. OS 표시 성공·전면 표시 성공·사용자가 실제로 읽었다는 뜻이 아니다. 알림함 기록을 먼저 커밋하고 OS 표시를 시도할 수 있다. 시작·복귀 시 awaiting_ack를 복원하며, 재표시가 필요한 건은 같은 occurrence ID로 선점·재전달한다. 표시 시도 시각·OS 결과·전면 전환 결과는 별도 운영 기록으로 남긴다.

OS 화면 표시와 저장소 커밋을 하나의 원자적 작업으로 묶을 수 없으므로 장애 경계에서 ‘정확히 한 번 화면 표시’를 보장하지 않는다. 누락 방지를 우선해 최소 한 번 전달을 시도하고, occurrence ID로 이미 떠 있는 창과 목록을 갱신해 일반적인 중복을 억제한다. 사용자가 본 직후 기록 전에 종료되면 다시 보일 수 있다.

알림 창을 X로 닫는 동작은 `확인`과 구별한다. 기본안은 미확인함에 남기고 즉시 다시 튀어나오지 않는 것이다. 명시적인 `확인`만 acknowledged로 만든다. 재표시 빈도·요약 정책은 사용자 설정으로 확정한다.

### 6.3 완료·일정 해제·휴지통의 영향

| 사용자 동작 | 알림 처리 |
|---|---|
| 메모 완료 | 미확인/대기 발생 건 취소. 원래 설정은 보관해도 enabled는 비활성 처리 |
| 완료 해제 | 과거 알림을 자동 재발화하지 않음. 다시 설정할지 선택 제공 |
| 단발 일정 이동 | 해당 상대 알림 재계산·유효성 토큰 갱신. 절대 알림은 유지하되 날짜 차이를 설명 |
| 반복 이번 회차 이동·완료 | 해당 키의 상대 알림만 재계산·취소, 다른 회차 불변 |
| 반복 선택 회차 이후 이동 | 세그먼트·예외 매핑 결과의 실제 날짜로 대상 알림 재계산. 확인·미루기 이력 보존, 구형 worker 토큰 거부 |
| 일정 해제 | 상대 알림 비활성화·발생 건 취소. 절대 알림은 유지 여부를 화면에 명확히 표시 |
| 메모 휴지통 이동 | 모든 활성 발생 건 취소. 편집·알림 창은 삭제 상태 표시 |
| 휴지통 복원 | 알림 설정 복구 여부를 확인하고 이미 지난 알림은 요약에서 처리 |
| 알림 해제 | 미확인/대기 발생 건 취소, 사용자 확인 이력은 보존 정책에 따름 |
| 진행 중/회신 대기/보류·수집함 정리·본문 체크 | 그 동작만으로 기한·알림·전체 완료를 바꾸지 않음. 체크 전부 완료도 알림 취소 사유 아님 |

같은 시점에 `완료`와 `알림 기한 도래`가 경쟁할 수 있다. 선점 전과 UI 게시 직전에 메모/해당 회차 상태, 설정 generation, delivery_revision, 규칙·예외 revision을 재검증한다. 취소 이벤트를 받은 알림 창은 즉시 상태를 갱신한다. 저장 직후 화면 표시가 잠깐 일어나는 경계 가능성은 시험하고 최소화한다.

## 7. 알림 실행과 Windows 전면 표시

### 7.1 실행 루프

1. 반복 일정은 영속 watermark와 유한 알림 horizon으로 회차를 생성·추적한다. 조회 범위 밖이라도 놓친 회차는 배치 따라잡기로 찾고 무한 미래 전체를 만들지 않는다. 생성 범위·예외 조회·너무 오래된 미확인 요약은 09를 따른다. 저장소에서 실행 가능한 가장 가까운 기한을 읽는다.
2. 다음 기한까지 기다리되 설정 변경·새 알림·절전 복귀·시간 변경 이벤트에 의해 다시 계산한다.
3. 기한 도래 시 트랜잭션으로 상태와 세대를 확인하고 원자적으로 선점한다.
4. 발생 건을 영속 앱 미확인함에 기록하고 awaiting_ack로 전이한다. 이미 기록된 같은 ID라면 기존 항목을 사용한다.
5. 동일 occurrence ID의 기존 알림 창을 찾거나 만든다. 필요한 경우 메모 스티키를 열고 접힘·최소화 상태를 복원하고 전면 표시를 시도한다. OS 결과와 관계없이 미확인함 항목은 유지한다.
6. 확인·다시 알림·취소를 저장한 뒤 모든 관련 화면에 반영한다.

장시간을 한 번에 타이머로 기다리며 영속 기록을 생략하지 않는다. 재시작 시 과거 기한과 lease 만료를 재검사한다. 스케줄 계산은 벽시계 UTC를 사용하고, 짧은 대기 측정은 가능한 경우 단조 시계를 사용해 시각 변경에 따른 비정상 대기를 줄인다.

### 7.2 전면 표시의 현실적 기준

Windows는 다른 프로세스가 전경 창을 가져오는 동작을 제한한다. 따라서 알림 때 창 복원·펼치기·전면 표시를 시도할 수 있지만 모든 상황에서 키보드 포커스를 빼앗는 동작은 보장할 수 없다. 이 제한은 [Microsoft SetForegroundWindow 문서](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow)에 근거한다.

수용기준은 다음처럼 구분한다.

- **앱 내부 보장:** occurrence가 저장되고 미확인 목록에 보이며 메모가 정상 상태이면 창을 만들거나 복원한다.
- **OS 허용 시 수행:** 접힘 해제, 최소화 복원, 전면 표시, 사용자가 허용한 알림·작업표시줄 주의 환기.
- **사용자 설정:** 소리, 항상 위, 민감 제목 표시, 알림이 입력을 방해해도 되는지.
- **잠금 상태:** 민감 본문을 노출하지 않고 잠금 해제 후 요약 제공. 실제 세션 잠금 감지는 선택 스택에서 검증한다.

전면 표시가 거부되면 반복 호출로 강제하지 않는다. 키 입력 흉내, 보안 우회, 무조건 관리자 실행 같은 방식을 해결책으로 삼지 않는다. 평상시 항상 위 설정과 알림 순간의 창 활성화를 혼동하지 않는다.

### 7.3 놓친 알림과 시계 변경

절전·최대 절전·PC 종료·앱 종료·프로세스 장애 동안의 즉시 표시는 불가능할 수 있다. 재실행·복귀 때 기한이 지난 미처리 건을 찾아 다음처럼 처리한다.

- 소수의 최근 알림은 한 번에 펼칠 수 있지만 기본은 놓친 알림 요약창으로 창 폭주를 막는다.
- 오래된 건도 조용히 폐기하지 않는다. 기간별 목록에서 확인·일괄 확인·다시 알림을 선택한다.
- 이미 확인·취소한 ID는 재표시하지 않는다. lease가 만료된 claimed는 실행권을 복구하고, awaiting_ack는 미확인함에 다시 노출한다. 마지막 표시 전에 중단되었거나 재전달 정책에 해당하면 awaiting_ack도 같은 ID로 선점·재표시한다.
- 시스템 시간을 앞으로 바꾸면 기한 지난 건을 다시 탐색한다. 뒤로 바꾸면 acknowledged 건을 다시 생성하지 않는다.
- 사용자가 시간대를 바꾸면 종일 날짜는 유지하고 시간 일정은 저장된 시점 기준으로 표시한다. 상대 알림 재계산이 필요한 정책 변경은 generation으로 구별한다.
- 공휴일 데이터가 갱신되어도 사용자가 정한 알림 시각을 임의 이동하지 않는다. 향후 영업일 알림 기능은 별도 설계다.

## 10. 구현 순서 및 출시 조건

1. 기존 창 생명주기·날짜 의미·알림 저장 방식을 조사하고 회귀 사례를 만든다.
2. 단발/반복 정의·정규 회차 키·예외·분할 모델과 revision 기반 명령을 먼저 구현한다.
3. 메인 캘린더, 원본 연결, 완료 취소선, 키보드 날짜 편집을 완료한다.
4. 별도 메모 창·별도 캘린더·좌우 분할·창 좌표 복원을 연결한다.
5. 반복 규칙·이번만/이후 이동·회차 완료를 09에 따라 연결하고 회차별 영속 알림·선점·확인·다시 알림을 구현한다.
6. 절전·재실행·시계 변경·프로세스 장애·다중 창 경쟁을 검증한다.
7. 실제 보안 정책에서 전면 표시 대안과 민감 정보 노출을 확인한다.
8. 일반 창 기반 기능 출시 후 바탕화면 표시의 독립 검증 여부를 결정한다.

출시 전 최소 산출물은 일정 구간 정의, 드래그 의미표, 창 닫기·종료 안내, 알림 상태 전이·복구 결과, 지원 Windows/배율/모니터 조합, 알려진 전면 표시 제한이다. 바탕화면 기능이 미검증이면 해당 기능만 제외할 수 있어야 하며 기본 메모·캘린더·알림의 품질을 대신하지 않는다.
